# PGO: 250-client Rust avatar A/B — laptop, 2026-10-08

**Observed CPU efficiency improvement for this workload.** PGO reduced median server CPU by 4.53% and CPU seconds per million built sends by 4.96%. Normalized CPU cost fell in all four paired comparisons (4.2–5.4%). Measured input was matched within 0.02%, all delivery/error gates passed, and median built work rose 0.41%. Median p95 applied gap changed only −0.30%, with one pair showing worse cadence and less built work; no reliable latency improvement or statistical significance is established.

The experiment uses two separate training runs followed by eight non-instrumented evaluation runs. Production code and default build settings are unchanged. [Retained evidence](results/pgo-client250-20261008-summary.json) includes compiler flags, build commands, hashes, training/profile metadata, all evaluation CSVs used for metrics/gates, process samples and paired comparisons.

## Method and provenance

Followed the [Rust compiler PGO workflow](https://doc.rust-lang.org/rustc/profile-guided-optimization.html): instrument a representative server, merge raw profiles with the matching LLVM tool, then rebuild using the merged profile. The A/B compares ordinary release and PGO builds of exactly the same server source at `e47c33e4967e5da234ab954e81a9a241f7e65aab` (server Git tree `5960e7b2efe37b16ef5098dfa1a7b704635b61fe`). It isolates PGO rather than repeating the earlier branch-versus-parent comparison.

Rust 1.99.0 / LLVM 23.1.1, locked release dependencies, explicit `x86_64-unknown-linux-gnu` target, incremental compilation off and two build jobs were fixed across all three stages. Each stage used its own target directory and the same absolute source directory. `-Cllvm-args=-pgo-warn-missing-function` was common; only the profile-generate/profile-use flag differed. No LTO or target-CPU tuning was added. Cargo fingerprints confirmed the actual compiler flags; the PGO build emitted no missing-profile or hash-mismatch warnings. This does not prove every function or behavior was exercised.

Two instrumented fresh-process runs trained on the accepted 250-client avatar workflow. Each passed all 34 workload, delivery, error and provenance gates and wrote one nonempty raw profile on successful shutdown. The files were 4,796,192 and 4,796,224 bytes; the merged profile is 9,470,896 bytes. `llvm-profdata show` reports IR instrumentation, 28,316 function records and 51,287,497,181 total counts. These are software instrumentation records/counts, not hardware branch measurements or a count of positively exercised functions. The largest counts include avatar encoding, byte writing, delta reading and bundle emission. Both raw profiles and the merged profile were unchanged after evaluation.

The instrumented training timings are excluded from the A/B. An initial build was cancelled before training because an empty `CARGO_ENCODED_RUSTFLAGS` overrode `RUSTFLAGS`; subsequent builds explicitly unset it, and neither that build nor any profiles from it entered the experiment. Its partial artifacts/log remain retained locally.

Evaluation reused the established Rust-client workflow: 250 dense colocated synthetic avatars, 20 ms updates, Unity-policy 60 FPS poses, zero jitter/drift, voice/P2P off and CPU-only server processing. The same ordinary Rust client binary from the preceding branch A/B was frozen for every run; it was neither instrumented nor rebuilt with PGO. The client, server fixtures and capture tools were frozen and hashed.

Eight fresh-process runs execute sequentially as `A B B A / B A A B`, four per variant, with 45 seconds of warmup and a 60-second measurement window after all clients become active. Server CPUs 2–9, client CPUs 10–15 and coordinator CPUs 0–1 remain disjoint. Server Rayon/Tokio and client Tokio each use four workers; Linux flush lanes are zero. This fixes the same affinity/worker configuration as the preceding comparison. Native Linux Ryzen 9 5900HX laptop, AC power and performance power profile; other user processes were not stopped.

## Limits

One host, one merged training profile and four evaluation processes per variant provide descriptive evidence. Applied gaps are one observer's update cadence, not network RTT or end-to-end latency for all receivers. Built work counts logical recipient sends before transport, not UDP packets. No runtime hardware branch counters were collected. Dense synthetic loopback avatars do not cover voice, churn, malformed traffic, backpressure, loss or remote networking.

Rust PGO flags applied to target Rust crates. Native C dependencies and the precompiled standard library were not rebuilt with instrumentation. A profile trained on this avatar workload cannot establish performance for those other workloads or another platform/compiler revision. PGO remains an experiment: the repository's production source and default release settings are unchanged.

## Delivery and checks

Both training runs and all eight evaluation runs passed all 34 workload/delivery/error/provenance gates. All 944 half-second evaluation samples retained 250 authenticated active states. Every evaluation run retained uninterrupted 249/249 observer coverage. Every sender generated/sent 3,000–3,001 items during its diagnostic window. The socket rate was 12,500 items/s in six runs, 12,502 in PGO run 5 and 12,502.33 in ordinary run 7 (at most 0.019% above the planned rate). Four sender records in each of those two runs differed by one between generated and sent counters; no send errors were reported. The client samples these counters separately using relaxed atomic reads, so the differences are consistent with snapshots crossing a send (an inference, not a demonstrated cause). These small window/counter variations are retained rather than described as exact input equality. No send, protocol, decode, malformed, unapplied-delta, missing/stale-peer, sequence/discontinuity, retransmit, WouldBlock, transport-drop or tick errors were reported by the checked counters. Both owned processes exited successfully in every run. No failed evaluation run or outlier was omitted.

All eight summaries were independently rederived from raw captures. Binary hashes and Cargo compiler-flag fingerprints were checked before evaluation. The stale-profile guard was checked with a preexisting raw file and refused training before launching processes; the helper CLI and whitespace checks passed. Two actual training runs verified successful profile writing and workload validation. CodeRabbit could not analyze the new helper because the review quota was exhausted (`rate_limit`); no clean automated review is claimed. Manual inspection and the real workflow checks completed.

## Reproduction and artifacts

Install `llvm-tools-preview` for the same Rust toolchain. Use an absolute fresh capture root, extract the same Git revision into its `source/` directory and create an empty `profiles/` directory. Keep one ordinary client binary fixed. The evidence records the exact environment/argument arrays for all three locked release builds. In each build, explicitly unset `CARGO_ENCODED_RUSTFLAGS`, set `CARGO_INCREMENTAL=0`, and retain the common flags and target. The stage-specific flags and target directories were:

| Stage | Additional RUSTFLAGS | Target directory |
|---|---|---|
| Ordinary | none | `build-release` |
| Training | `-Cprofile-generate=<absolute root>/profiles` | `build-generate-clean` |
| PGO | `-Cprofile-use=<absolute root>/profiles/merged.profdata` | `build-use` |

After the instrumented build, collect the two validated training runs:

```sh
python3 -B scripts/perf/train-avatar-pgo.py \
  --root captures/pgo-client250-20261008 \
  --client captures/client250-branches-20261008/series/frozen/client
```

Use the toolchain’s `lib/rustlib/x86_64-unknown-linux-gnu/bin/llvm-profdata` to merge only those two new raw files and inspect the merged profile; exact merge/show argument arrays and profile hashes are in the evidence. Rebuild the PGO server, prepare the build manifest with the selected baseline/candidate/client SHA-256 values, and run:

```sh
python3 -B scripts/perf/compare-avatar-revisions.py \
  --baseline captures/pgo-client250-20261008/build-release/x86_64-unknown-linux-gnu/release/basis-server-console \
  --candidate captures/pgo-client250-20261008/build-use/x86_64-unknown-linux-gnu/release/basis-server-console \
  --client captures/client250-branches-20261008/series/frozen/client \
  --build-manifest captures/pgo-client250-20261008/build-manifest.json \
  --output captures/pgo-client250-20261008/evaluation \
  --clients 250 --blocks 2 --warmup-seconds 45 --window-seconds 60 \
  --server-cpus 2-9 --client-cpus 10-15
```

The shown paths identify the completed experiment; choose a fresh capture root for another run. Training rejects preexisting raw profiles and existing output directories. Adjust affinities only for another host and keep both variants matched. The binary profiles, frozen binaries and full local captures remain under `captures/pgo-client250-20261008/`; they are ignored by Git, with their hashes and relevant evidence committed. Reuse a merged profile only with compatible compiler/source/build settings, or retrain.
