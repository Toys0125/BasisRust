# 1,500-client Rust avatar PGO A/B — laptop, 2026-10-08

**All 1,500 clients remained active, with much slower observed avatar cadence at this load.** Median applied p95 gap was 426.43 ms for ordinary release and 416.005 ms for PGO. The prior 250-client session was about 33 ms; that is descriptive cross-session context, not a controlled scaling curve.

The existing PGO binary showed modest median improvements: built logical sends/s +1.90%, server CPU −0.58%, CPU seconds per million built sends −2.32%, and applied p95 gap −2.44%. Three of four pairs favored PGO on work, normalized CPU and p95; one favored ordinary release. These are descriptive observations from four processes per variant, not established significance or a universal improvement.

**The original strict series is invalid:** every corrected run failed its cumulative absolute-zero retransmit gate because retransmits had accumulated before measurement. Those counters stayed constant throughout all eight measured windows. All other 33 original gates passed, including full 60-second observer windows, 1,499/1,499 peer coverage, sender progress, population, exits and decoding/error checks. Separate steady-window checks do not overwrite original validity.

[Retained evidence](results/pgo-client1500-20261008-summary.json) includes every corrected and preliminary attempt, commands/provenance, binary/profile/config/tool hashes, raw CSVs and process fields used for metrics/gates, retransmit counts and exact supplemental controller source.

## Measurement correction and retained attempts

The preliminary baseline's observer covered only 59,823 ms and failed the original 60,000 ±100 ms window checks. The observer starts on its first inbound avatar after the marker, while sender diagnostics start independently from the marker. The original capture tool quit the client as soon as sender diagnostics finished. At high load this could end reception before the observer completed its later-starting window.

`scripts/perf/avatar_benchmark.py` now maintains readiness and reception for a two-second grace **after** the fixed measurement window. CPU sampling/interpolation and server/sender diagnostic endpoints are unchanged. The observer still caps its own statistics at the requested 60 seconds. The real corrected runs validate the timing fix; the capture test suite passed 18 tests with one Windows-only skip. No production server/client source or build settings changed.

The preliminary cohort is retained separately: one completed ordinary run, one completed PGO run, and a third PGO attempt interrupted to fix measurement timing. All raw datasets, errors and artifact hashes are preserved; the whole preliminary cohort is excluded from corrected medians because its measurement procedure differed. No performance outlier was selectively removed.

The standard coordinator stopped on its first strict gate failure. Supplemental local controllers completed the scheduled diagnostic runs while preserving every original gate and invalid status. Their exact source, hashes and invocation are retained in JSON. Gate failures were not suppressed or relabeled as a fully valid series.

## Interpretation limits

Cumulative health retransmit counters include connection/ramp and warmup activity before the measured window. The original validator requires absolute zero in every sample. Nonzero premeasurement values therefore fail that strict gate even when the count stays constant during measurement. The report retains both original validity and separate first/last/min/max counts and steady-window checks; it does not claim the entire run was retransmission-free.

Four corrected processes per variant on one laptop provide descriptive observations, not statistical significance. The observer measures update cadence at one receiver, not network RTT or end-to-end latency for all receivers. Built work counts logical recipient sends before transport, not UDP packets. Dense loopback avatars omit voice, churn, malformed traffic, loss, remote networking and other production distributions. The fixed workers/affinity and 250-client training profile do not establish maximum host capacity, an optimal 1,500-client profile or platform-default performance. No hardware branch counters were collected.
