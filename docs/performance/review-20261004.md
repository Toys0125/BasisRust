# Fresh Windows performance review — 2026-10-04 UTC

Six fresh release benchmark runs completed and passed delivery validation. This review compares the server before PRs #18–#26 (`58c107e`) with merged main (`624ae0c`) using one frozen merged client. Historical results are separate context.

## Findings and priorities

1. **The fresh server comparison does not establish a speedup.** Merged means were 9.5% longer for p50 gaps, 4.7% longer for p95, 7.8% lower for applied items/s and 4.0% lower for combined CPU. The controls themselves ranged from 64.97 to 76.18 ms p50 and 9,213 to 10,848 applied items/s. One ordered pair favored merged cadence and the other favored before-merges cadence. These two repeats do not establish a stable PR regression. Lower CPU with lower delivery cadence is not an equal-work efficiency improvement.

2. **Prioritize packet emission and traffic reduction.** At 1,000 clients, flush cost was 3.37–3.64 ms/tick, 54–56% of measured tick work. Server kernel CPU was 53–55% of process CPU and client kernel CPU was 78%. Egress was 147.6–182.6 MB/s, or 1.18–1.46 Gbit/s of UDP payload before headers. This exceeds a physical 1 Gbit/s link in both runs. The source sends each assembled datagram through `try_send_to`, with receiver groups flushed in parallel; reducing datagrams/fanout or testing a bounded Windows batching/concurrency change is a better next experiment than raising worker counts blindly. Existing ETW evidence supports investigating the Windows UDP/loopback path, but no new stack attribution was collected here.

3. **Delivery correctness is good; cadence remains a capacity limit.** All 1,000 clients progressed, but median observer gaps were 117–148 ms and p95 was 179–200 ms. The observer applied about 6.8–8.0 updates per peer per second despite approximately 50 inbound updates per client per second. Coalescing/adaptive fanout is intentional, so zero delivery errors does not mean every input update was forwarded. Define an acceptable applied-update cadence alongside CPU and bandwidth targets before calling this workload production-ready.

4. **Resolve measurement variation before accepting small optimizations.** Both variants varied materially, and fresh pre-merge controls also differ from historical results. A next optimization should use repeated crossover runs with frozen binaries, record tick/slice behavior and host background CPU, and retain peer/error gates. A realistic spatial/quality distribution and voice workload, followed by a capped remote-link test, is needed to assess deployment performance; this review measured dense synthetic loopback.

## Historical comparison

The latest archived Rust 1.99 750-client cohort used the same CPU-only fixture, loopback, four client workers and 45/60-second windows, but a different frozen client and older source. Its two-run means were 47.27/79.93 ms p50/p95, 6.005 combined CPU cores and 14,568 observer items/s.

Fresh merged means changed by +63.5% p50, +51.7% p95, -16.1% combined CPU and -36.5% applied items/s versus that cohort. These between-session differences do not establish a code regression or speedup; the fresh pre-merge controls are the stronger comparison.

Fresh pre-merge controls also averaged 70.58/115.79 ms p50/p95 and 10,030 applied items/s, already slower than that archived cohort. Differences outside PRs #18–#26, including the frozen client/observer, older server changes and host/session variation, remain possible causes; this review does not isolate them.

The older October 1 default 1,000-client runs recorded 200–230 ms p50, 340–411 ms p95, 4.25–4.46 million built logical sends/s and 105–111 MB/s UDP payload. They used Rust 1.95, the older MTU/cadence/allocator configuration, 15-second warmup and the compute-enabled fixture. Both fresh and old binaries use CPU distance paths in these default builds. The settings differ enough that changes cannot be attributed to PRs #18–#26.

## Validation and measurement meaning

- Every run kept all requested clients authenticated and active in all 30 readiness samples.
- Each observer saw all 749 or 999 expected peers, with zero missing or end-of-window stale peers over 500 ms. This does not assert that no peer ever had a 500 ms gap during the window.
- All sender records stayed connected, progressed with at least 2,900 successful sends, and reported zero send errors.
- Observer decode errors, malformed items, unapplied deltas and non-newer sequences were zero. Server protocol errors, retransmits and UDP WouldBlock were zero. The merged server also reported zero non-reliable datagram drops.
- Clients exited with status 0. Server stop statuses are retained in the JSON; Windows console-control exit is expected harness behavior.
- A CPU core is one process CPU-second per elapsed second; divide cores by 16 for this machine's utilization fraction. CPU/UDP endpoint deltas cover about 58 seconds inside the marked 60-second observer window.
- Update gaps are intervals between successful avatar applications at one observer, not end-to-end latency or RTT. Logical work counters record built fanout; observer items show actual application at that receiver.
- Egress counts UDP payload bytes before IP/link overhead and stayed on loopback. It does not measure the physical NIC or establish production capacity.
- Memory figures are maxima among two-second samples, not allocation counts or whole-run high-water marks. Commit charge is not kernel socket allocation.

## Scope and reproduction

Host: Windows 11 Pro build 26100, Ryzen 7 9800X3D, 8 physical/16 logical cores, high-performance power plan. Rust 1.99.0 MSVC release builds, locked dependencies, default features, no GPU, no CPU affinity. Client Tokio workers=4; server default Windows Rayon/cadence settings. Dense colocated synthetic poses, 20 ms movement interval, zero jitter/spread, 60 fps Unity policy, voice/P2P/reconnect disabled. Background applications were left running. No physical-network load, new native tracing, Linux run or production workload was performed.

Raw CSVs/logs, frozen binaries, hashes, host metadata, exact commands and validators are retained under `captures/performance-review-20261004/` (ignored locally). `experiment.json` identifies both server revisions; the shared runner's `workload.json.git_revision` identifies the harness checkout, so it is not the pre-merge server revision. Each validated summary adds the correct `server_revision`.

Build the server/client with `cargo build --locked --release --jobs 2` in their separate workspaces. Run the checked-in [Windows harness](../../scripts/perf/run-windows-avatar-workload.py) with `--server <frozen-server.exe> --client <frozen-client.exe> --server-config docs/performance/fixtures/avatar-cpu-only-server.xml --clients 750 --workers 4 --warmup-seconds 45 --window-seconds 60 --no-server-avatar-diagnostics --output <new-directory>`. For the 1,000-client diagnostic check, set `--clients 1000` and omit `--no-server-avatar-diagnostics`. Clear Rayon, Tokio, avatar budget/slice and deployment-password overrides. Validate the captures before accepting results.
