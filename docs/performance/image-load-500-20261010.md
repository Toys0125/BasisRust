# Image relay and cache workload: 500 clients

One successful release-build sample on 2026-10-10 delivered all three 5 MiB JPEG shares with 500 authenticated clients connected. All 1,488 live image copies and nine cached copies matched the source bytes. There were no workload disconnects, missing chunks, malformed images, integrity failures, fragment errors, server image drops, or protocol errors.

The [machine-readable results](image-load-500-20261010.json) include phase measurements, configuration, source and binary hashes, validation counts, and limitations. Raw logs, all 1,497 receiver/image completion records, and 0.5-second process samples are retained locally under `captures/image-governor-500-20261010/run-500-final/`.

## Workload and environment

- Linux, AMD Ryzen 9 5900HX, 16 logical processors, 32 GiB RAM. Server and generator share the host, without CPU affinity. UDP uses loopback.
- Production `ServerState` and transport workers, wrapped by a benchmark example that writes read-only one-second telemetry. Server Tokio workers: 16; client Tokio workers: four. The console's idle allocator trimming is absent from this wrapper.
- 500 authenticated headless clients, without ongoing avatar or voice traffic. Three share concurrently; each targets 496 recipients. The three remaining clients request all three images from cache after live delivery finishes.
- A valid synthetic 2048x2048 JPEG, exactly 5,242,880 bytes, split into 320 BasisVR 16 KiB chunks. Each share has a separate image GUID. Every receiver checks spawn metadata, owner identity, chunk indices and lengths, uniqueness, and every payload byte against the fixture. The compressed image is 5,211,237 bytes; valid JPEG comment metadata adds 31,643 bytes to reach exactly 5 MiB. This measures image transport, without texture decoding/rendering at 500 recipients.
- Fixture SHA-256: `7e02fa44351cccb904a9155e589df40aafc1313afdc6465b74993d420c15e3f1`. The generator reproduces this hash with Pillow 10.2.0.
- Ten seconds of connected idle baseline, live transfers, three seconds between phases, cached downloads, 15 seconds of connected settling, then client shutdown and five seconds of disconnected idle. All 500 clients remain connected through settling.

Configuration names and defaults match BasisVR:

| Setting | Value |
|---|---:|
| `ImageCacheEnabled` | `true` |
| `ImageCacheMaxMegabytes` | 512 |
| `ImageCacheMinimumPerOwnerMegabytes` | 32 |
| `ImageShareEgressMegabitsPerSecond` | 200 |
| `ImageShareDownloadMegabitsPerSecond` | 200 |
| `ImageShareEgressEnforcementPercent` | 150 |

The client charges image payload bytes once per recipient against a 200 Mbps aggregate fanout rate per sharer. Thus one 5 MiB image to 496 recipients requires about 104.0 seconds. The server admission budget includes 150% enforcement headroom and two seconds of burst credit. This normal, paced workload does not measure rejection of abusive unpaced uploads.

The runner detects completion on a 0.5-second polling interval; the table above uses client timestamps at actual completion. Each cache recipient downloads 15 MiB total, within the default 50 MB initial download burst. These requests exercise the cache/replay path but do not establish sustained download throttling at 200 Mbps.

All 479,040 expected chunks were received uniquely, representing 7,848,591,360 image payload bytes across 1,497 complete copies. The entire run sends 7,974,635,275 UDP payload bytes in 8,289,625 datagrams, including connection setup, ACKs, pings, and teardown. UDP byte counters exclude IP/UDP headers.

Reliable transport retries 1,637 packets during live transfer and another 1,183 during cache downloads; final payload validation still passes without application duplicates. Teardown adds 1,500 retries after the client process exits. There are no observed socket WouldBlock events or reorder-budget rejections. Sampled peak reliable queue depths are 24,378 packets during relay and 40,423 during cache downloads; pending reliable depths reach 1,490 and 384 respectively. All queues drain to zero before settling ends.

Three complete cache entries retain 15,783,552 accounted bytes (15.05 MiB), including metadata/accounting overhead. Owner departure releases all cache entries and accounted bytes; final player count and transport queue depths are zero. RSS remains elevated after disconnect, at 207.82 MiB sampled peak during disconnected idle. This wrapper does not trim the allocator, and this one run does not distinguish allocator retention from repeated-cycle memory growth. RSS excludes kernel socket buffers.

## Transport fixes exposed by preparation

The first small preflight showed that Rust received normal LiteNetLib fragmented image chunks as individual messages. The server now reassembles ReliableOrdered and ReliableUnordered traffic before application delivery, supporting negotiated fragment sizes and charging payloads plus assembly metadata to existing global/per-peer receive budgets. ACKed ordered fragments and completed messages remain retained through queue pressure; malformed fragments or structural limits disconnect the captured session. Session cleanup releases retained state.

The headless client also reassembles fragments and handles singular and late-join batch network-ID assignment. Its existing reliable receive path still dispatches complete application messages in arrival order; benchmark accounting accepts spawn and chunks in either order and requires both before recording completion. This is not a claim of live Unity/C# client interoperability.

Preparation also corrected harness readiness, phase-boundary telemetry, and fanout arithmetic. One earlier 500-client attempt stopped before any image uploads because the harness ignored batch network-ID assignment; that attempt is retained under `run-500/` and excluded from these image measurements. Three client review findings were fixed: portable MTU constants, enough assemblies for a reliable window under fragment loss, and preserving disconnect cleanup on an image-worker join error.

Validation includes 90 passing transport tests (two ignored), 135 passing server-core tests, and 124 passing client-core tests (two ignored), with targeted UDP fragment loss/reordering/duplicate/backpressure coverage and full-window client reassembly coverage. The full server workspace with the GPU feature passes 377 tests (six ignored). Workspace formatting and strict Clippy pass for the server's default and GPU feature builds and the client. No build or review ran concurrently with the successful 500-client measurement.

## Reproduce

From the repository root, with Rust, Python 3, and Pillow installed:

```bash
cargo build --release --manifest-path BasisRustServer/Cargo.toml \
  -p basis-server-core --example image-load-server
cargo build --release --manifest-path BasisRustClient/Cargo.toml \
  --example image-load-client
python3 scripts/perf/generate-image-fixture.py --output captures/image-fixture.jpg
python3 scripts/perf/run-image-workload.py \
  --output captures/image-load-500-new \
  --image captures/image-fixture.jpg
```

Output directories/files must be new. The runner writes the exact commands, effective image settings, modified-source hashes, executable hashes, samples, and validation summary. The measured runtime was built on `c825c4fad25cfc392d33729475d9943ab4e227f6` with the source changes committed alongside this report; consult the recorded hashes rather than treating that base commit alone as the tested revision.

This sample establishes complete image delivery and cleanup for this workload on this host. It does not establish WAN/NIC performance, combined avatar/voice capacity, simultaneous cache downloads to 500 peers, GPU performance, rendering latency, or long-duration repeated-share memory behavior.
